## 1. Overview & Architectural Boundaries

Slice V4 bridges in-browser Zoom Video SDK live sessions with the Sharon ESL attendance, settlement, and dispute architecture.

In the legacy Zoom Meetings (S2S) architecture, attendance was derived from server-to-server webhooks for desktop meetings. Under Zoom Video SDK, sessions run directly in the browser via WebRTC under deterministic room topics `lesson-<booking_id>`.

### Seam Rule
V4 is an **evidence producer**, not a verdict judge:
- V4 ingests session events and telemetry into `AttendanceAudit` rows.
- Existing settlement logic (`apps/bookings/services/attendance_probe.py` and `apps/bookings/services/settlement.py`) reads `AttendanceAudit` to adjudicate completion, no-show, and disputes.
- V4 must never alter or bypass the F0 state machine invariants.

## 2. Telemetry Ingestion Channels

V4 employs a dual-evidence pipeline to ensure resilience against webhook dropouts and network partitions.

### 2.1 Video SDK Webhook Receiver
- **Endpoint:** `POST /api/v1/integrations/video-sdk/webhooks/`
- **Security & Validation:**
  1. **URL Validation Challenge (`endpoint.url_validation`):**
     - Zoom sends `{ "event": "endpoint.url_validation", "payload": { "plainToken": "..." } }`.
     - The endpoint computes `encryptedToken = hmac_sha256(plainToken, ZOOM_VIDEO_SDK_WEBHOOK_SECRET).hexdigest()`.
     - Responds with HTTP 200: `{ "plainToken": "...", "encryptedToken": "..." }`.
  2. **Webhook Signature Verification:**
     - Headers: `x-zm-request-timestamp`, `x-zm-signature`.
     - Construct message: `v0:{x-zm-request-timestamp}:{raw_request_body}`.
     - Verify signature against `ZOOM_VIDEO_SDK_WEBHOOK_SECRET` using timing-safe comparison (`hmac.compare_digest`).
     - Reject requests older than 5 minutes (replay defense).
- **Events Ingested:**
  - `session.started`: Classroom session launched.
  - `session.ended`: Classroom session closed.
  - `session.user_joined`: Participant joined the session.
  - `session.user_left`: Participant left the session.

### 2.2 Client-Side Heartbeat Fallback
To protect against webhook delivery latency or edge network drops:
- **Endpoint:** `POST /api/v1/bookings/<id>/video-heartbeat/`
- **Cadence:** In-browser client sends heartbeat pings every 30 seconds while connected to the media stream.
- **Payload:** `{ session_name, user_identity, elapsed_seconds, stream_status: { audio: bool, video: bool } }`.
- **Authentication:** Scoped to the authenticated user and validated booking ID.
- **Idempotency:** Telemetry records merge seamlessly with webhook records using deterministic `zoom_session_id`.

## 3. Evidence Mapping & `AttendanceAudit` Records

All ingested telemetry produces `AttendanceAudit` records conforming to the existing schema:

```python
AttendanceAudit.objects.create(
    booking=booking,
    classification=classification,  # 'teacher' | 'student' | 'unknown'
    identity='video_sdk',
    participant_id=user_identity,
    zoom_session_id=session_join_id,
    joined_at=event_timestamp,
    left_at=leave_timestamp,        # updated on user_left or session.ended
    duration_minutes=calculated_dwell,
    raw_payload=event_payload,
)
```

### Identity & Role Classification
1. **Tutor (`teacher`):**
   - Matching `user_identity == str(booking.teacher.user_id)` or `role_type == 1`.
2. **Student (`student`):**
   - Matching `user_identity == str(booking.student_id)` or `role_type == 0`.
3. **Unknown (`unknown`):**
   - Any unrecognized user identity or external connection.
   - Preserved as raw evidence for audit logs; **never counted toward attendance or settlement**.

### Dwell Calculation & Reconnect Grace
- Dwell time is computed from continuous presence.
- **5-minute disconnect grace:** In accordance with `ZOOM_ATTENDANCE.md`, reconnect gaps $\le 5$ minutes are merged into continuous presence to accommodate transient browser or Wi-Fi reconnections.
- Retries and out-of-order deliveries (e.g. `user_left` arriving before `user_joined`) converge deterministically using `zoom_session_id`.

## 4. Preservation of F0 Attendance Semantics

The core settlement rules documented in `ZOOM_ATTENDANCE.md` and `SETTLEMENT_PATHS.md` remain strictly intact:

| Situation at T+10m | Evidence Recorded | Adjudicated Outcome |
| :--- | :--- | :--- |
| Student recorded as joined, and `probe_video_session` positively answers `not_started` | Positive proof student waited and tutor never started room | `teacher_no_show` (refund, bonus credit, tutor strike) |
| Tutor recorded as joined, student absent | Positive proof tutor opened room and student did not arrive | `student_no_show` (tutor paid, credit forfeited) |
| Tutor live in room | Active participant session detected | `in_progress` (no no-show) |
| Neither joined, probe answers `unknown`, network timeout, or ambiguous signal | **Missing or ambiguous evidence** | **Deferred; NEVER a no-show**. If still unresolved at lesson end $\rightarrow$ `DISPUTED` with open `DisputeCase`. |

### Lesson Completion Rule
- A lesson is marked `completed_pending_memo` if and only if credited tutor dwell time $\ge 20$ minutes during the scheduled lesson window.
- If credited dwell $< 20$ minutes and no no-show was adjudicated, the lesson ends as `DISPUTED`.
