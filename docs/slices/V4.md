## 1. Overview & Architectural Boundaries

Slice V4 bridges in-browser Zoom Video SDK live sessions with the Sharon ESL attendance, settlement, and dispute architecture.

In the legacy Zoom Meetings (S2S) architecture, attendance was derived from server-to-server webhooks for desktop meetings. Under Zoom Video SDK, sessions run directly in the browser via WebRTC under deterministic room topics `lesson-<booking_id>`.

### Seam Rule
V4 is an **evidence producer**, not a verdict judge:
- V4 ingests session events and telemetry into `AttendanceAudit` rows with `identity='video_sdk'`.
- Existing settlement logic (`apps/bookings/services/attendance_probe.py` and `apps/bookings/services/settlement.py`) reads `AttendanceAudit` to adjudicate completion, no-show, and disputes.
- V4 never alters or bypasses the F0 state machine invariants; all booking status changes use `transition_booking()`.

## 2. Implemented Components

### 2.1 Video Session Probe (`apps/bookings/services/video_session_probe.py`)
- **Function:** `probe_session(booking) -> str`
- **Return Values:**
  - `STARTED`: The session is live AND the tutor's `user_identity` (their user UUID) is in it.
  - `NOT_STARTED`: Zoom positively reports that no tutor ever joined a session for this topic (e.g. 404 resource not found, empty sessions list, or sessions exist but tutor was never present).
  - `UNKNOWN`: Transport errors, connection timeouts, HTTP 429/5xx, auth failures, missing credentials, or unparseable responses. Defers adjudication; never counts as absence.
- **REST Protocol:**
  - Generates short-lived Video SDK API JWT (`HS256`, 1-hour expiration) using `ZOOM_VIDEO_SDK_KEY` and `ZOOM_VIDEO_SDK_SECRET`.
  - Queries `GET https://api.zoom.us/v2/videosdk/sessions?topic=lesson-<booking_id>`.
  - Queries `GET https://api.zoom.us/v2/videosdk/sessions/{session_id}/users` if users are not inline.
  - Implements exponential backoff and jitter for transient errors (429, 5xx) with configurable retry attempts.
  - Cyclomatic complexity kept $< 12$ via modular helper functions (`_get_matching_sessions`, `_session_contains_tutor`, `_user_list_contains_tutor`).

### 2.2 Webhook Receiver (`apps/integrations/views.py` & `apps/integrations/urls.py`)
- **Endpoint:** `POST /api/v1/integrations/video-sdk/webhooks/` (and trailing slash alias `POST /api/v1/integrations/video-sdk/webhook/`).
- **Security:**
  - **URL Validation Challenge (`endpoint.url_validation`):** Zoom CRC verification. Responds with `{ "plainToken": "...", "encryptedToken": hmac_sha256(plainToken, secret) }`.
  - **HMAC Signature Verification:** Timing-safe comparison (`hmac.compare_digest`) against `ZOOM_VIDEO_SDK_WEBHOOK_SECRET` (falling back to `ZOOM_WEBHOOK_SECRET_TOKEN` if unset).
  - **Replay Protection:** Rejects any request with timestamp skew $> 300$ seconds.
  - **Row-Locked Dispatch:** Uses `select_for_update()` on the target `Booking` row to guarantee serialised event processing.

### 2.3 Attendance Ingestion Engine (`apps/integrations/services/video_attendance.py`)
- **Participant Classification:**
  - Matches participant `user_identity` against `str(booking.teacher.user.id)` $\rightarrow$ `classification='teacher'`.
  - Matches participant `user_identity` against `str(booking.student.id)` $\rightarrow$ `classification='student'`.
  - Unmatched stranger or external ID $\rightarrow$ `classification='unknown'`, `participant_email=''`. Unrecognized identities never affect attendance, dwell, or lesson status.
- **Event Handling:**
  - `session.user_joined`: Creates or updates `AttendanceAudit` record keyed by `zoom_session_id`. If tutor joins a `CONFIRMED` booking, advances booking to `IN_PROGRESS` via `transition_booking()`.
  - `session.user_left`: Updates `leave_time_utc`, computes dwell duration in minutes. Merges reconnect gaps $\le 5$ minutes as continuous presence.
  - `session.started`: Logs session activation and sets `raw_payload`.
  - `session.ended`: Closes open audit records for the session.
- **Late Telemetry Hazard Defense:**
  - If a join/leave event arrives after a lesson has already been marked as `TEACHER_NO_SHOW` or `STUDENT_NO_SHOW`, the system flags a late-arrival hazard, quarantines the booking to `DISPUTED`, and opens a `DisputeCase` for tribunal review.
- **Idempotency:**
  - Retried webhooks deduplicate on `zoom_session_id` and `event_id`, preventing duplicate audit records or double-counting minutes.

## 4. Preservation of F0 Attendance Semantics

The core settlement rules documented in `ZOOM_ATTENDANCE.md` and `SETTLEMENT_PATHS.md` remain strictly intact:

| Situation at T+10m | Evidence Recorded | Adjudicated Outcome |
| :--- | :--- | :--- |
| Student recorded as joined, and `probe_video_session` positively answers `not_started` | Positive proof student waited and tutor never started room | `teacher_no_show` (refund, bonus credit, tutor strike) |
| Tutor recorded as joined, student absent | Positive proof tutor opened room and student did not arrive | `student_no_show` (tutor paid, credit forfeited) |
| Tutor live in room | Active participant session detected | `in_progress` (no no-show) |
| Neither joined, probe answers `unknown`, network timeout, or ambiguous signal | **Missing or ambiguous evidence** | **Deferred; NEVER a no-show**. If still unresolved at lesson end $\rightarrow$ `DISPUTED` with open `DisputeCase`. |
